Identity Security Personas & Unified RBAC Permissions

Common roles for identity threat detection and response (ITDR), mapped to Microsoft Defender Unified RBAC (URBAC) permissions. URBAC is the only model for Defender for Identity tenants onboarded since March 2025. Response actions add a second layer: the portal permission authorizes the click, and a service account in Active Directory or Entra ID performs the change.

📄

Guidance only

These personas and permission mappings are illustrative examples, not a configuration baseline. They reflect Microsoft Learn documentation captured on 3 August 2026, they are static, and Microsoft's permission catalog, role names, and RBAC rollout change over time. Verify every permission against your own tenant before you assign it, and treat this page as a starting point rather than an authoritative source.

📌

Two layers authorize every response action

The Response (manage) URBAC permission lets a user submit Disable user, Force password reset, or Revoke session in the Defender portal. The change itself is executed by a separate identity account: the domain controller's LocalSystem account by default in Active Directory (v3.x sensors always use LocalSystem; v2.x can optionally use a dedicated gMSA action account), and a Microsoft-managed enterprise application in Entra ID. Portal RBAC and the action account are configured and audited independently.

1The Unified RBAC permissions in play

Every identity task in the Defender portal maps to one of these URBAC permissions across three groups: Security operations, Security posture, and Authorization and settings. Build custom roles from the specific permissions a persona needs, and scope data access to particular AD domains or OUs where required.

How the legacy groups map to URBAC

Tenants onboarded before March 2025 used three per-workspace security groups, named with an Azure ATP (workspace name) prefix. LEGACY Azure ATP Administrators maps to Security data basics (read) plus Alerts (manage) plus Authorization (read and manage), Security settings (all permissions), and System settings (read and manage). Azure ATP Users maps to Security data basics (read) plus Alerts (manage) plus Security settings (all permissions) plus System settings (read). Azure ATP Viewers maps to Security data basics (read) plus Core security settings (read) plus System settings (read).

4Where the portal permission meets the action account

MDI response actions split authorization in two. The Defender portal checks the signed-in user's URBAC or Entra role before the action is submitted. The change is then carried out by a service account in the target identity system, which is configured and permissioned separately. Plan both layers, or a persona will see the button, click it, and watch the action fail.

🔐

The action account is not the directory service account

MDI uses two distinct on-premises accounts. The Directory Service Account reads Active Directory for entity data and needs read-only rights across all objects. The action account writes changes for Disable user (Read and Write userAccountControl) and Force password reset (Reset password, plus Read and Write pwdLastSet). Keep them separate, since they carry different permission scopes. On v3.x sensors both roles always use the domain controller's LocalSystem account, with no gMSA option; a dedicated gMSA applies only to v2.x sensors or specific cross-domain scenarios.

6Best-practice notes

  • Build custom URBAC roles from specific permissions. A Tier-1 identity analyst needs only Security data basics (read); a responder adds Alerts (manage) and Response (manage). Combine the exact permissions rather than assigning a broad Entra role.
  • Plan both authorization layers for response. Response (manage) lets a user click Disable user, but the action account must be configured and permissioned for the change to land. For Entra-targeted actions, the user also needs an Entra role such as SOC Identity Responder.
  • Prefer SOC Identity Responder for Tier-2. This dedicated Entra role covers the identity response actions without the broader reach of Security Operator, which makes it the tighter least-privilege choice for responders.
  • Keep the DSA and action account separate. The Directory Service Account is read-only; the action account writes. Reusing one gMSA for both over-grants the read account.
  • Scoped roles cannot see posture. The Exposure Management section is hidden from users with an MDI scoped assignment, so an Identity Posture Administrator needs an unscoped role to review ISPM recommendations.
  • Sensor installation lives outside URBAC. System settings (manage) generates the access key in the portal, but installing the sensor on a domain controller requires local administrator rights on that server.
  • Entra roles override URBAC. Security Administrator in Entra is automatically treated as an MDI administrator, so it is broader than a scoped custom role. Reach for the URBAC permission when you want a tight boundary.
  • Elevate high-privilege roles just in time. Grant Security Administrator and Global Administrator through Microsoft Entra Privileged Identity Management (PIM) as time-boxed, approval-gated activations rather than standing assignments.
  • Keep dedicated break-glass accounts. Maintain at least two cloud-only emergency-access accounts excluded from Conditional Access, and reserve Global Administrator for them.
  • Separate duties and audit. Split configuration (Core and System settings) from response (Response), and monitor changes to entity tags, exclusions, sensors, roles, and every response action in the unified audit log.
