Cloud App Security Personas & Unified RBAC Permissions

Common roles for securing SaaS and cloud apps, mapped to Microsoft Defender Unified RBAC (URBAC) permissions alongside the Defender for Cloud Apps built-in roles. Unlike Endpoint and Identity, Cloud Apps integration with URBAC is opt-in and still in preview as of August 2026, so both models are in play, and several tasks stay on Entra ID roles or the app connectors entirely.

📄

Guidance only

These personas and permission mappings are illustrative examples, not a configuration baseline. They reflect Microsoft Learn documentation captured on 3 August 2026, they are static, and Microsoft's permission catalog, role names, and RBAC rollout change over time. Verify every permission against your own tenant before you assign it, and treat this page as a starting point rather than an authoritative source.

⚠️

Cloud Apps URBAC is preview and opt-in

Defender for Cloud Apps is only partly onboarded to Unified RBAC, and the integration is marked Preview. Endpoint and Identity activate URBAC by default; Cloud Apps does not, an administrator turns it on. Activating URBAC for Cloud Apps discontinues four scoped roles (App/instance admin, User group admin, Cloud Discovery global admin, Cloud Discovery report admin) with no URBAC equivalent, and the deactivation path does not document restoring them. App governance stays on Entra ID roles regardless, except the OAuthAppInfo hunting table. Weigh the loss of app-level and group-level scoping before activating.

1The Unified RBAC permissions in play

When URBAC is activated for Cloud Apps, these permissions govern the workload. They apply portal-wide, not with a Cloud Apps qualifier, and the official mapping table pins each built-in role to a permission set (shown below).

🗺️

How the built-in roles map to URBAC

On activation, the four non-scoped built-in roles translate to permission sets. Local Global administrator gets Security data basics (read), Alerts (manage), and all of Authorization, Security settings, and System settings. Local Security operator gets read plus Alerts (manage), Security settings (all), and read on Authorization and System settings. Local Security reader gets read plus read on Authorization, Security settings, and System settings. The scoped roles have no mapping and are dropped.

🔐

A governance action can be authorized and still fail

Suppose an operator with Response (manage) triggers "suspend user in Salesforce." The Defender portal authorizes the click, then calls the Salesforce API using the connector's credentials. If that connector was set up with read-only rights, the suspend fails no matter how much portal permission the operator holds. Governance effectiveness depends on the connector's granted scope in the target app, which is decided during connector setup by a SaaS admin, not by MDA RBAC.

6Best-practice notes

  • Decide on URBAC activation deliberately. Cloud Apps URBAC is opt-in and preview. Activating it discontinues the App/instance, User group, and Cloud Discovery scoped roles with no equivalent, so confirm no delegation relies on them first.
  • Mind the governance-action gap. The Security Operator built-in role manages alerts but cannot suspend a user or make a file private. Acting on users or non-file objects needs Security Administrator or Global administrator, which is the sharpest least-privilege limitation in Cloud Apps.
  • App governance is Entra-only. Assign Entra roles for OAuth app policies and remediation. URBAC touches app governance only through the OAuthAppInfo hunting table.
  • Conditional Access App Control needs two grants. The session policy lives in MDA, but traffic only reaches the proxy through an Entra Conditional Access policy. Grant Conditional Access Administrator alongside the MDA role.
  • Portal permission does not equal connector permission. A governance action is only as capable as the connector behind it. If a suspend or unshare fails, check the connector's granted scope in the target SaaS app before adjusting RBAC.
  • Use Compliance Administrator for file work. File policies, DLP, and file governance actions are covered by the Compliance administrator role, without granting the broader activity and OAuth policy rights of a Security Administrator.
  • Elevate high-privilege roles just in time. Grant Security Administrator, Cloud App Security Administrator, and Global Administrator through Microsoft Entra Privileged Identity Management (PIM) as time-boxed, approval-gated activations.
  • Keep dedicated break-glass accounts. Maintain at least two cloud-only emergency-access accounts excluded from Conditional Access, and reserve Global Administrator for them.
  • Separate duties and audit. Split policy configuration (Core security settings) from governance actions (Response), and monitor changes to connectors, policies, scoped admins, and the governance log in the audit trail.
