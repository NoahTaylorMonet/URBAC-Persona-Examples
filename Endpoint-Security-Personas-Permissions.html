Microsoft Defender for Endpoint · Unified RBAC

Endpoint Security Personas & Unified RBAC Permissions

Common roles for managing endpoint security, mapped to Microsoft Defender Unified RBAC (URBAC) permissions. URBAC is the default model for every new Defender for Endpoint tenant provisioned since early 2025. Device configuration in Intune, security settings management, and the Defender for Endpoint APIs sit outside URBAC, and those handoffs are called out.

📄

Guidance only

These personas and permission mappings are illustrative examples, not a configuration baseline. They reflect Microsoft Learn documentation captured on 3 August 2026, they are static, and Microsoft's permission catalog, role names, and RBAC rollout change over time. Verify every permission against your own tenant before you assign it, and treat this page as a starting point rather than an authoritative source.

📌

What URBAC covers, and what device groups still scope

Unified RBAC governs the Microsoft Defender portal at security.microsoft.com and replaces the legacy Defender for Endpoint role model. Data access is still bounded by device groups (machine groups): a role only sees and acts on the device groups it is assigned. Endpoint security policies (antivirus, firewall, EDR, ASR) live in Microsoft Intune under Intune RBAC, and unattended automation authenticates through Azure AD app permissions, neither of which URBAC touches.

🗂️

Example device group naming pattern

Model device groups the same way you would tier any other resource, for example: Tier0-DomainControllers, Tier1-HighValueAssets, Region-East / Region-West, Mission-A, Contractor-Systems. Assign the Security Administrator persona to all device groups, and scope Tier-2/Tier-3 responder personas to only the region or mission groups they own, so a regional analyst never sees devices outside their segment.

⚠️

Role-assignable groups: only for Global Reader / Global Administrator

isAssignableToRole only matters when a group is assigned an actual Microsoft Entra directory role (see the Global Reader / Global Administrator persona below). Creating a role-assignable group requires Privileged Role Administrator (or Global Administrator), the flag is set at creation and is immutable, membership must be Assigned (no dynamic groups), and the group cannot be nested. The other personas on this page are Defender custom roles assigned to an ordinary Entra security group from the Defender portal’s own Roles page — that group does not need to be role-assignable, and creating it only requires a role that can create security groups (for example Groups Administrator), plus Authorization (manage) in Defender or Global Administrator to complete the role assignment. Verify this distinction against your tenant before requiring Privileged Role Administrator for a group that does not need it.

1The Unified RBAC permissions in play

Every endpoint task in the Defender portal maps to one of these URBAC permissions across three groups: Security operations, Security posture, and Authorization and settings. Build custom roles from the specific permissions a persona needs, then bind each assignment to the device groups it should reach.

2The personas

Job-shaped roles you actually assign, each expressed as the URBAC permission set it needs plus the device group scope that bounds it. Where a persona configures endpoint policy or drives automation, the Intune role or API permission it additionally requires is noted. Prefer the narrowest permission set and the tightest device group scope that covers the task.

Click a persona’s icon to copy a ready-to-run Microsoft Graph PowerShell snippet that provisions the underlying Entra security group for that role. The Defender custom role, its permission grants, and PIM activation settings still have to be finished in the Defender and Entra portals — there is no general-availability public API for either, so a true one-click “Deploy to Azure” button cannot fully provision this end to end (see the footer for why).

App-only automation shows the pattern

A SOAR playbook that isolates a device authenticates app-only against the WindowsDefenderATP API and needs the Machine.Isolate application permission granted with admin consent, plus the OAuth client-credentials token from api.securitycenter.microsoft.com. URBAC does not apply to app registrations, so a Defender portal permission alone will not authorize the call. Grant only the specific API permissions the playbook uses (for example Machine.Isolate and Machine.LiveResponse), rather than Machine.ReadWrite.All across the tenant.

6Best-practice notes

  • Build custom URBAC roles from specific permissions. Combine the exact permissions a persona needs (for example Security data basics plus Alerts plus Response for a Tier-2 responder) instead of assigning a broad Entra role. This is the least-privilege path URBAC is designed for.
  • Scope every role to device groups. Permissions grant capability; device groups decide which machines the role reaches. A regional Tier-1 role scoped to "North America workstations" cannot see servers or other regions, even in the same tenant.
  • Entra roles override URBAC. Assigning Security Administrator in Microsoft Entra grants the full endpoint URBAC equivalent automatically, so it is broader than a scoped custom role. Reach for the URBAC permission when you want a tight boundary.
  • Global Administrator is over-privileged, not sidelined. Under URBAC, Global Administrator is auto-mapped to the full permission set (equivalent to Security Administrator), including live response and settings, across all device groups. Treat it as break-glass because of that reach, and do day-to-day work under a scoped role.
  • Portal permission does not equal API permission. A persona with Response (manage) can isolate a device in the portal, but a scripted isolation needs the Machine.Isolate app permission. If an automation fails with an access error, the missing piece is almost always an app registration permission.
  • Advanced live response needs File collection too. The legacy "advanced" tier maps to both Advanced live response (manage) and File collection (manage) in URBAC. Grant them together, and enable the Live response feature toggle under Advanced features first.
  • Keep endpoint policy in Intune RBAC. Core security settings (manage) covers onboarding and portal settings, not antivirus, firewall, EDR, or ASR policy. Those need an Intune role such as Endpoint Security Manager.
  • Elevate high-privilege roles just in time. Grant Security Administrator and Global Administrator through Microsoft Entra Privileged Identity Management (PIM) as time-boxed, approval-gated activations rather than standing assignments.
  • Recommended PIM activation settings. For Security Administrator and other high-privilege groups: require MFA on activation, require approval, cap the activation duration at 8 hours, and assign members as Eligible rather than Active so nothing stands elevated by default.
  • Keep dedicated break-glass accounts. Maintain at least two cloud-only emergency-access accounts excluded from Conditional Access, and reserve Global Administrator for them.
  • Separate duties and audit. Split configuration (Core security settings) from response (Response and live response), and monitor changes to indicators, custom detections, roles, and device groups in the unified audit log.
  • Document and review on a cadence. Record tier assignments, device group structure, and role mappings; train assignees on activation and escalation; and revisit the whole model periodically as personas, device inventory, and business needs change.

7Validate the rollout

Before handing a role to its owner, sign in as a test account in each tier and confirm both what should work and what should correctly fail. A permission that silently does not apply, or a device group boundary that leaks visibility, is much easier to catch here than after go-live.
